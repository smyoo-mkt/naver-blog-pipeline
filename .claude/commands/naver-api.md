`scripts/naver-data.py`로 네이버 실측 데이터를 모아 **수요 분석 리포트**를 만든다.
답할 질문은 4개다:

1. 사람들이 이 주제를 **어떤 문구로** 검색하는가
2. 내가 쓰려는 그 문구는 **실제로 검색되는 문구인가**, 머릿속에서 만든 조합어인가
3. 사람들이 실제로 **무엇을 묻는가** (질문 제목 + 본문 원문)
4. 그 니즈는 **수임으로 이어지는 니즈인가**

경쟁도·진입 판정은 이 4개 다음에 오는 종속 정보다. 순서를 바꾸지 않는다.

대상: $ARGUMENTS

## 절대 규칙

1. **수치는 스크립트 출력만 기재한다.** 추정·보간·기억으로 채우지 않는다. 실패한 칸은 `측정실패`로 남긴다.
2. **질문·니즈는 원문 그대로 인용한다.** 요약해서 뭉개면 소재 가치가 사라진다. 오타·구어체도 그대로 둔다.
3. **문서수(블로그·지식iN·카페 total)는 문구 실존의 근거가 아니다.** 네이버는 형태소를 쪼개 합집합을 센다.
   실측 예: `법인 세무기장 위탁 절차 안내`는 아무도 검색하지 않는 조합어인데 블로그 문서수가 891건 나온다.
4. **문서수는 시점 간 비교가 불가능하다.** 대조군도 이번 런에서 다시 측정한다. 옛 `work/*-keyword-data.md` 숫자를 베끼지 않는다.
5. **레지스트리를 수정하지 않는다.** 행 추가·상태 변경은 큐레이터/운영자 몫이다. 대조와 경고까지만.
6. 읽기 전용 수집이다. 리포트 결론을 "발행 결정"으로 표시하지 않는다.

## 실행 순서

### 0. slug 확정

영문 kebab-case. `ls work/ | grep <slug>`로 충돌 확인. 같은 slug가 있으면 **덮어쓰지 말고**
"기존 행 재실측인가, 새 키워드인가"를 운영자에게 묻는다.

### 1. 실제 검색 문구 지도

```
python3 scripts/naver-data.py volume <타겟 키워드>
python3 scripts/naver-data.py acdeep <타겟 키워드>
python3 scripts/naver-data.py ac <상위 문구...>
```

- `volume`은 `relKeyword`로 연관 문구를 자동 확장해 돌려준다. **입력이 주제 수준이어도 여기서 실제 문구가 나온다.**
  타겟 클러스터에 속하는 것만 남기고 무관한 업종·지역어는 버린다. `< 10`은 `<10`으로 적는다 (0으로 쓰지 않는다).
- `acdeep`은 검색창이 실제 타이핑을 학습해 만든 제안어다. **광고 데이터보다 날것에 가깝다.**
  제안어의 **개수와 방향**을 본다. 개수가 적으면 수요가 얕거나 독자에게 아직 언어가 없는 것이다.
  금액 앵커(`5만원`, `10만원`)가 붙는지는 독자의 시세 감각 유무를 알려준다.

### 2. 문구 실존 판정 ← 이 커맨드의 핵심

검증하고 싶은 문구(제목 후보, 질문형 키워드, 인자로 준 추가 문구)를 모아 한 번에 판정한다:

```
python3 scripts/naver-data.py exists <문구1> <문구2> ...
```

4개 신호가 한 표로 나온다 — 광고 검색량(PC/모바일) · DataLab 비영개월/총개월 · 자동완성 개수 · 지식iN/블로그 문서수.

**판정 규칙:**

| 신호 조합 | 판정 |
| --- | --- |
| 광고 합계 ≥ 10 **또는** DataLab 비영개월 > 0 | ✅ 실제 검색되는 문구 |
| 광고 `<10` + DataLab `0/0` + 자동완성 0개 | ❌ **실검색 문구 아님** (조합어). 제목·키워드로 쓰지 않는다 |
| 광고 `<10` + DataLab 데이터 있음 | ⚠️ 초저빈도. 단독 타겟 불가, 본문 소제목 수준 |

- 광고 API는 입력 문구를 그대로 되돌려주므로 **`미인지`는 거의 안 뜬다.** `<10`이 실질적 하한 신호다.
- 결정적 신호는 **DataLab 비영개월 수**와 **자동완성 개수**다. 둘이 동시에 0이면 조합어로 확정한다.
- 문서수 컬럼은 판정에 쓰지 않는다 (절대 규칙 3). 참고용으로만 적는다.

### 3. 사람들이 실제 묻는 것

```
python3 scripts/naver-data.py kin  <타겟 키워드> <상위 문구...>
python3 scripts/naver-data.py cafe <타겟 키워드> <상위 문구...>
```

- **제목만 보지 말고 본문(`body`)을 읽는다.** 본문에 독자의 실제 상황(매출·업종·지역·받은 견적 금액)이 있고,
  그게 본문 골격의 원재료다. 지식iN = 질문, 카페글 = 하소연·후기. 니즈의 감정 온도는 카페에 있다.
- **노이즈 필터:** 세무사무소·비상주사무실·법무법인 홍보글, 전문칼럼 연재물은 사람 목소리가 아니다.
  세지 말고 제외하고, 제외했다는 사실을 리포트에 적는다.
- 질문을 3~6개 패턴으로 묶고, 각 패턴에 **대표 문장을 원문 그대로** 붙인다. 비중(최다/다수/중)도 표시한다.
- 질문자들이 공통으로 붙이는 조건(매출·업종·지역)이 있으면 그것이 곧 독자 세그먼트다.

**검색량 대비 질문 수가 많으면 수요가 검색창이 아니라 질문창으로 흐른다** = SERP가 답을 못 주고 있다는 신호다.

### 4. 니즈 → 문의 의도 매핑 (전환 거리 판정)

`guides/conversion-config.md`의 "카피 소구 방향"을 읽고, 3단계의 각 질문 패턴을 **실측 수임률**에 매핑한다.

| 문의 의도 | 실측 수임률 | 전환 거리 |
| --- | --- | --- |
| 신규기장 × 창업 1년 미만 | 40.7% | 최단 |
| 신규기장 | 32.7% | 짧음 |
| 세무사이관 (기존 세무사 불만) | 31.3% | 짧음 |
| 급여·4대보험 | 26.8% | 보통 |
| (전체 평균) | 21.2% | — |
| 가격 문의 | 14.9% | 멂 |
| 신고 대리 | 11.4% | 멂 |
| 정부지원금 자체 | 5.7% | 최장 |

- 검색량이 큰 패턴이 반드시 전환되는 패턴은 아니다. **두 축을 따로 적는다.**
- 가격·신고 문의가 최다 패턴이어도 그것을 CTA 각도로 삼지 않는다. 본문에서는 그 질문에 답하고,
  **결론은 "매달 관리 = 기장"으로 닫는 경로**를 리포트에 명시한다.
- 조건절에 "개업했는데", "이번에 사업자 냈는데", "세무사 바꾸려는데"가 보이면 최우선 각도다.

### 5. 시즌

```
python3 scripts/naver-data.py trend <상위 문구...>
```

월별 상대지수(기본 최근 19개월, `--from=`/`--to=`로 오버라이드). **절대 검색량이 아니라 그룹 내 상대값**이다.
피크월을 찾고 세무 일정(신고기한)과 붙는지 해석한다. 전년 동월 대비 추세도 본다.
1회성 스파이크(세법개정안 발표 등)를 시즌으로 착각하지 않는다.

### 6. 공급 분석 — SERP가 그 니즈에 답하는가

```
python3 scripts/naver-data.py blog <상위 문구...> <대조군 문구...>
```

문서수와 상위 10건의 발행일·블로거·제목이 나온다. **제목을 반드시 읽는다.**

- 상위 제목의 **지배 문법**을 뽑는다 (예: 전부 "금액보다 X가 중요하다" 한 프레임).
- 3단계에서 뽑은 질문 패턴을 하나씩 대조한다: **이 질문에 답하는 글이 상위에 있는가?**
  없는 패턴이 곧 빈틈이고, 그게 이 커맨드의 최종 산출물이다.
- **광의매칭 오염 판정:** 상위 제목에 타겟과 무관한 지역 세무사무소 홍보글·특수법인 글이 섞여 있으면
  그 문서수는 정면 경쟁 모수가 아니다. 오염이면 실제 제목을 인용해 근거를 남긴다.

### 7. 진입 가능성 + 레지스트리 대조

레지스트리 전문(54KB)을 읽지 말고 컬럼만 뽑는다:

```
awk -F'|' '/^\| [a-z0-9-]+ \|/ {print $2, "|", $3}' work/content-registry.md
```

문자열 겹침·의미 인접으로 이미 점유된 행을 찾는다. 겹치면 **그 행의 note만** `grep '<slug>' work/content-registry.md`로
읽어 점유 범위를 확인한다. 대조군 문구는 6단계 문서수 측정에 **반드시 포함한다** (절대 규칙 4).

**바이 = 검색량 ÷ 문서수 × 1000.** 표에 `1 : N`(직관적 경쟁도)과 `바이`(레지스트리 note 표기)를 병기한다.

| 바이 | 1차 판정 |
| --- | --- |
| > 50 | ✅ 진입 |
| 10 ~ 50 | ⚠️ 조건부 |
| < 10 | ❌ 레드오션 |

이 절대 기각선은 **1차 필터일 뿐이다.** 2차 판정 둘:

- **광의매칭 보정** — 문서수가 오염 판정되면 그 바이로 기각하지 않는다. `오염-판정보류`로 적는다.
- **레지스트리 상대 순위** — 대조군과 서열화하고 배수를 적는다 (예: "tax-accountant-change 0.36보다 22배 유리").

1차와 2차가 상충하면 **한쪽으로 결론내지 말고 양쪽을 다 적어 게이트1로 넘긴다.** 유입 KPI와 전환 KPI 사이의 결정은 운영자 몫이다.

## 리포트 작성

`work/<slug>-keyword-data.md`에 아래 구조로 쓴다. 데이터가 없는 섹션은 비우지 말고 삭제한다.

```markdown
# <타겟> — 검색 수요 실측

> 측정일 YYYY-MM-DD · `scripts/naver-data.py` (검색광고 + 블로그 + 카페 + 지식iN + DataLab + 자동완성)
> 실측값이다. 브리프플래너는 이 수치를 **추정으로 덮어쓰지 말 것.**
> 문서수는 시점 간 비교 불가 — 다른 날짜 리포트의 숫자와 나란히 놓지 말 것.

## 1. 사람들이 실제 쓰는 검색 문구
표: 문구 | PC | 모바일 | 합계 | 경쟁 | 자동완성 노출
→ 클러스터 합산 한 줄. 자동완성 트리(코드블록)로 확장 방향.
→ 판정: 쿼리 깊이 / 방향 몇 갈래 / 금액 앵커 유무.

## 2. 문구 실존 판정
표: 문구 | 광고(PC/모바일) | 트렌드 비영/총 | 자동완성 | 판정
→ ❌ 판정된 문구는 **제목·키워드 후보에서 제외**임을 명시.

## 3. 사람들이 실제 묻는 것 (지식iN N건 · 카페 N건)
표: # | 패턴 | 대표 문장(원문 인용) | 비중
→ 질문자 공통 조건(매출·업종·지역) 한 단락 = 독자 세그먼트.
→ 제외한 노이즈(홍보글·연재칼럼) 명시.
→ 검색량 대비 질문 수 비교 한 줄.

## 4. 니즈 → 문의 의도 (전환 거리)
표: 패턴 | 문의 의도 | 실측 수임률 | 전환 거리 | CTA 각도로 쓸 수 있는가
→ 최우선 각도 1개 + 가격·신고 니즈를 기장으로 닫는 경로.

## 5. 시즌 (DataLab 월별 상대지수)
코드블록으로 월별 지수 → 시즌 판정 (피크월 + 세무일정 연결 + 즉시 발행 시 시즌 유입 유무).

## 6. 공급 분석 — SERP가 답하는가 (<1순위 문구> 상위 10)
발행일 분포 → 상위 제목의 지배 문법(제목 + 블로거 + 날짜) →
**질문 패턴별 답변 존재 여부 표: 패턴 | 상위에 답하는 글 | 빈틈?**

## 7. 진입 가능성
표: 문구 | 검색량 | 문서수 | 1:N | 바이 | 판정
→ 광의매칭 오염 경고(근거 제목 인용).
### 대조군 (기존 레지스트리 행이 이미 점유)
표: 문구 | 합계 | 문서수 | 바이 | 소유 slug
→ 상대 서열 한 단락.

## 8. 기획 결론
- SERP가 답하지 않는 것 (= 빈틈)
- 본문 골격의 근거 (자동완성이 아니라 지식iN/카페 어느 패턴인지)
- 최강 진입 각도 1개 + 그 각도의 전환 거리
- 발행/리프레시 타이밍
- 자기잠식 경계 (어느 slug가 무엇을 점유했고 이 글은 무엇으로 차별화하는지)
- ❌ 실존 판정 탈락 문구 목록 (다음 세션이 다시 후보로 올리지 않게)
```

## 마무리 출력

리포트 경로와 함께 **3줄 이내**로 요약한다: ① 1순위 문구와 실존·바이 판정 ② 가장 강한 니즈 패턴과 그 전환 거리
③ 게이트1에서 운영자가 결정해야 할 쟁점 1개.

이어서 기획으로 갈지(`/naver-post <키워드>`), 다른 문구를 더 볼지 묻고 멈춘다.
