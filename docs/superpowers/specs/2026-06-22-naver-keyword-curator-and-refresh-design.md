# 네이버 파이프라인 확장 설계: 키워드 큐레이터 + 콘텐츠 리프레시

작성일: 2026-06-22
대상: `naver-blog-pipeline` (세무기장 전환 전용)

## 배경 / 문제

기존 4개 에이전트(브리프플래너→리서처→라이터→SEO에디터)는 전부 **글 1편 단위**다. 그러나 가이드 스스로 *C-Rank가 생명*이라 적었듯, C-Rank는 블로그 전체의 누적·일관성·지속성을 본다. 지금 비어 있는 축은 두 가지:

1. **앞단** — 어떤 키워드를 쓸지 발굴하고, 자기잠식(같은 키워드 중복 발행)을 막는 주체가 없다. 브리프플래너는 "키워드 1개를 받는다"고 가정만 한다.
2. **뒷단** — 발행 후 끝난다. 세법은 매년 개정되는데(`시점주의` 플래그를 만들기만 하고 만료시키는 루프가 없음), 성과 낮은 글을 다시 손보거나 시즈널 글을 재발행하는 메커니즘이 없다.

## 목표

- 신규 에이전트 2개를 기존 파이프라인 양 끝에 붙인다: `naver-keyword-curator`(앞), `naver-content-refresh`(뒤).
- 단일 진실원(SSOT) 파일 `work/content-registry.md`로 모든 키워드의 생애주기(후보→기획→발행→갱신필요)를 추적한다.
- YMYL 휴먼 게이트 철학 유지: 리프레시는 글을 자동 수정하지 않고 워크리스트만 낸다.

## 비목표 (이번 범위 제외)

- 내부링크/에디토리얼 캘린더 매니저(3번) — 별도 후속.
- 전환 자동 측정 대시보드(Amplitude 등 연동) — 성과는 수기 기입.
- 이미지/도표 자동 생성.
- 새 슬래시 커맨드(`/naver-keywords` 등) — 후속으로 가능, 이번엔 안 만듦.

## 1. 데이터: `work/content-registry.md` (SSOT)

키워드 1개 = 1행. 발굴부터 갱신까지 한 행에서 추적한다. 마크다운 표(세무사도 읽기 쉬움). 파일 상단에 **상태값 정의 + 기입 규칙** 헤더 주석을 둔다(포맷 가이드를 별도 파일로 빼지 않고 여기 흡수 → SSOT 유지).

| 필드 | 의미 | 누가 채움 |
|---|---|---|
| `slug` | 영문/숫자 식별자 (발행 전엔 비움 가능) | 큐레이터/플래너 |
| `keyword` | 타겟 키워드 | 큐레이터 |
| `intent` | 정보성 / 전환성 | 큐레이터 |
| `cluster` | 토픽 클러스터 (필러 / 서브-OO) | 큐레이터 |
| `cta_type` | conversion-config 글 유형 (법인기장/개인기장/환급/롱테일) | 큐레이터 |
| `priority` | 우선순위 점수 = 전환가치 × 진입난이도(역) | 큐레이터 |
| `season` | 시즈널 월 (해당 시 1·3·5·7월 등, 상시면 빈칸) | 큐레이터 |
| `status` | `후보` → `기획` → `발행` → `갱신필요` | 전 단계 |
| `published_at` | 발행일 (YYYY-MM-DD) | 운영자 |
| `fact_basis_year` | 핵심 사실 기준연도 (예: 2026 세율) | 리서처/리프레시 |
| `perf` | 성과 메모 `조회=, 톡톡=, 측정일=` (수기) | 운영자 |
| `last_refreshed` | 마지막 갱신일 | 리프레시 |
| `note` | 중복 사유·차별화 각도 등 메모 | 큐레이터/리프레시 |

상태 전이: `후보`(큐레이터 추가) → `기획`(브리프 승인 후) → `발행`(운영자) → `갱신필요`(리프레시 플래그). 행이 수백 개로 커지면 연도별 분할, 지금은 단일 파일.

## 2. 에이전트: `naver-keyword-curator` (파이프라인 앞단)

- **frontmatter tools:** Read, Write, WebSearch, WebFetch
- **작업 전 읽기:** `work/content-registry.md`, `guides/naver-seo-guide.md`(3단계 키워드 전략·시즈널 캘린더), `guides/conversion-config.md`(전환목표·재산제세 제외)
- **할 일:**
  1. **발굴** — WebSearch로 자동완성·지식iN·네이버 SERP 상위 글을 보고 롱테일+로컬 / 질문형 / 시즈널 키워드 후보 생성. 재산제세(상속·증여·양도)는 전환 대상 아니므로 제외.
  2. **자기잠식 체크** — registry 기존 행과 의미 중복 검사. 중복이면 새 후보 대신 *"기존 slug 보강"* 으로 표시(`note`에 사유).
  3. **클러스터·우선순위** — 필러/서브 매핑, `priority` 점수(전환가치 × 진입난이도 역수).
  4. registry에 `status=후보` 행 추가 + 다음에 쓸 Top N 추천 출력.
- **핸드오프:** 추천 키워드 1개 → `naver-brief-planner`. 브리프플래너의 입력이 이제 registry에서 나온다.

## 3. 에이전트: `naver-content-refresh` (파이프라인 뒷단)

- **frontmatter tools:** Read, Write, WebSearch, WebFetch
- **작업 전 읽기:** `work/content-registry.md`, 해당 `work/<slug>-research.md`(시점주의·기준연도), 가이드.
- **3개 신호로 갱신 대상 판정:**
  1. **세법개정·시점만료** — research의 `시점주의`·`fact_basis_year` vs 현행(WebSearch 1차 출처 확인). 어긋나면 플래그. (YMYL 핵심)
  2. **성과** — registry `perf` 칼럼을 읽어 저성과 글 리라이트 후보.
  3. **시즈널** — 시즈널 캘린더 역산, 신고철 2~3주 전 재발행 대상.
- **출력:** `work/refresh-worklist.md` — 대상 글 + 사유 + 권장 액션(사실수정 / 리라이트 / 재발행). registry 해당 행 `status=갱신필요`, `note` 기록, `last_refreshed` 갱신.
- **핸드오프 (중요):** 직접 고치지 않는다. 워크리스트만 낸다. 운영자 승인 후 기존 파이프라인(리서처→라이터→SEO에디터 + ⛔게이트2 세무사 감수) 재진입. YMYL 게이트 유지.

## 4. 통합 (기존 파일 보강 — 새 가이드 없음)

- `README.md`: 구조도·흐름도에 큐레이터(앞)·리프레시(뒤) 추가. 갱신된 흐름:
  ```
  큐레이터 → registry → 브리프플래너 → ⛔게이트1 → 리서처 → 라이터 → SEO에디터 → ⛔게이트2 → 발행
                ↑                                                                              │
                └────────────  리프레시(성과·개정·시즈널) → 워크리스트 ←──────────────────────┘
  ```
- `naver-brief-planner`: 입력을 "registry에서 추천된 키워드"로 명시 + 브리프 승인 시 registry `status=기획`, 발행 시 `status=발행` 갱신 책임 한 줄 추가.
- 새 슬래시 커맨드는 만들지 않는다. 두 에이전트 모두 `/agents` 명시 호출 또는 자연어 트리거.

## 성공 기준 (검증)

- `work/content-registry.md`가 헤더 규칙 + 빈 표 스켈레톤으로 존재한다.
- `.claude/agents/naver-keyword-curator.md`, `.claude/agents/naver-content-refresh.md`가 frontmatter(name/description/tools) + 시스템 프롬프트로 존재하고, 기존 4개 에이전트의 형식·톤과 일치한다.
- `README.md` 구조도·흐름도가 6개 에이전트 + 2개 신규 산출물(registry, refresh-worklist)을 반영한다.
- `naver-brief-planner.md`가 registry 입력/상태갱신 책임을 명시한다.
- 두 에이전트의 핸드오프 문구가 휴먼 게이트(자동 발행/자동 수정 금지)를 깨지 않는다.
